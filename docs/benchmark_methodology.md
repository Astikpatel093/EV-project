# Benchmark methodology

Two benchmark programs are built from `benchmarks/`:

| Program | What it is | Output |
|---|---|---|
| `ev33_bench` | the project's own harness: fixed datasets, repeated runs, validation of every result, peak heap bytes | `benchmarks/results.csv` (one row per measurement) and a console log |
| `ev33_gbench` | Google Benchmark (vendored v1.9.1) micro-benchmarks of merge/quick sort, Dijkstra, Prim, Kruskal, knapsack DP and interval partitioning, with Google Benchmark's own complexity fit | Google Benchmark's console / JSON output |

The numbers shown in the website, the desktop app and the README come from
`benchmarks/results.csv`; nothing is typed in by hand.

## Datasets

Generated by `benchmark_data_generator` (or in memory by `ev33_bench`) from **seed 12345** with
the library's own xorshift64* generator, so the same seed gives the same data on every platform.
`data/generated/metadata.json` records, for every file, its parameters, record counts and an
FNV-1a checksum; `benchmark_data_generator --out data/generated --verify` regenerates everything
in memory and compares (current state: 47/47 files reproduce).

| Set | Vertices | Edges | Variants |
|---|---|---|---|
| B1 | 100 | 300 | connected-varied, connected-equal, disconnected (4 components) |
| B2 | 500 | 1,500 | same |
| B3 | 1,000 | 3,000 | same |
| B4 | 5,000 | 15,000 | same |
| B5 | 10,000 | 30,000 | same |
| B6 | 50,000 | 150,000 | same |
| D100 / D200 / D400 | 100 / 200 / 400 | n(n−1)/4 (half of all pairs) | dense |

Other families: sort keys (random, sorted, reversed, few distinct; 10³–10⁶), sorted keys with
10⁵ search queries, placement instances with 25–800 candidates at budgets of 10 %, 25 % and 50 %
of the total cost, one-day session sets of 10³–10⁶ sessions, random dense matrices 32–512, and
200-trip samples of the generated `small`, `medium` and `large` scenarios for the two trip
planners. Connected graphs are built as a random spanning tree plus random extra edges with no
duplicates or self-loops; weights are integers so that totals are exact.

## Measurement procedure

1. Inputs are generated **before** timing. Each algorithm in a group runs on the **same** input
   object (for example, Dijkstra, Bellman–Ford, Floyd–Warshall, Prim and Kruskal on one `Graph`).
2. Each measurement is repeated (5 times by default, 3 for the slow Θ(V³) cases, 1 for the
   slowest) and the **median**, minimum and maximum wall-clock time are reported
   (`std::chrono::steady_clock`).
3. Results are **validated outside the timed region**: shortest-path trees by an optimality
   certificate and by the other algorithms; spanning trees Prim = Kruskal; knapsack DP = branch
   and bound, greedy reported as a percentage of the optimum; activity selection vs. depth;
   Strassen vs. classical; planners by re-simulation. A failed check writes `FAIL` and makes the
   program exit with code 2.
4. A checksum of every result goes into a `volatile` sink so the optimiser cannot delete the work.
5. Peak heap bytes are measured by replacing the global `operator new/delete` in the benchmark
   executable (bytes allocated above the level before the call).
6. Algorithms with quadratic or worse cost are run only where they finish in seconds
   (Bellman–Ford up to B4, Floyd–Warshall up to B2 and on the dense sets, quick sort with a
   first-element pivot on sorted input up to 10⁴ keys).

## CSV columns

`algorithm, family, dataset, variant, input_size, vertices, edges, candidates, budget, seed,
compiler, build_type, repetitions, median_ms, min_ms, max_ms, peak_bytes, validation, note`

Empty cells mean "not applicable" (for example `vertices` for a sort).

## How to reproduce

```
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
build/benchmarks/benchmark_data_generator --seed 12345 --size all --out data/generated
build/benchmarks/ev33_bench --out benchmarks/results.csv          # about 25 s
build/benchmarks/ev33_bench --only graphs --reps 9                 # one family
build/benchmarks/ev33_gbench --benchmark_filter=Dijkstra
```

Families for `--only`: `sorting, searching, graphs, dense, placement, scheduling, matrix,
planning`. Always benchmark a **Release** build; the `build_type` column records it.

## Environment of the committed results

`benchmarks/results.csv` (228 rows, 0 validation failures) was produced on a cloud Linux VM:
Intel Xeon @ 2.80 GHz, 2 vCPUs, 7 GB RAM, gcc 13.3.0, `-O3 -DNDEBUG`, single-threaded. Absolute
times will differ on other machines; the comparisons between algorithms on the same input are
what the results are for.

## Selected results (from `benchmarks/results.csv`)

| Measurement | Result |
|---|---|
| Sorting 10⁶ random keys | merge sort 138 ms, quick sort median-of-3 119 ms, random pivot 136 ms |
| Quick sort, first-element pivot, 10⁴ already-sorted keys | 23.5 ms (n² behaviour) vs 0.12 ms median-of-3 and 0.09 ms merge sort |
| Dijkstra / Prim / Kruskal, B6 (50,000 vertices) | 35.3 ms / 52.2 ms / 22.2 ms |
| Floyd–Warshall vs Dijkstra from every source, D400 dense | 110 ms vs 269 ms (Floyd wins on dense graphs) |
| Knapsack, 800 candidates, budget 25 % | DP 10.8 ms (table 800 × 10,750), least-cost branch and bound 0.43 ms (696 nodes), greedy 0.06 ms at 99.94 % of the optimum |
| Interval partitioning, 10⁶ sessions | 538 ms; bays = maximum overlap |
| Trip planning, 200 trips of the large city | exact planner 1.90 s (198 feasible), leg planner 142 ms (199 feasible) |

The table is a snapshot; regenerate the CSV for current numbers. The website's Benchmarks page
plots every family on log–log axes directly from the file.

## Threats to validity

* Two vCPUs on a shared VM: background load can move individual times; the median of repeated
  runs and the min/max columns show the spread.
* Small inputs (< 0.01 ms) are close to timer resolution.
* Peak bytes count only heap allocations made through `operator new` in the measured call.
* The trip-planner rows compare different algorithms on 200-trip samples, not full days.
