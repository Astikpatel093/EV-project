# Data

## What is in the repository

| Folder | Content | Origin |
|---|---|---|
| `data/sample/` | a 10-node network written by hand, 3 existing stations, 6 candidates, 3 vehicles, 8 trips; every expected answer worked out in its `README.md` | **synthetic, hand-made** |
| `data/scenarios/small, medium, shock, large, adversarial` | the five cities the app, website, CLI demo and regression tests use | **synthetic**, `ev33_gen --all --seed 33` |
| `data/generated/` | benchmark datasets B1–B6, D100–D400, sort keys, placement instances, session sets (59 MB, not committed; `metadata.json` is) | **synthetic**, `benchmark_data_generator --seed 12345` |

**No bundled file describes a real place, operator, vehicle or person.** Coordinates are placed
near latitude 0°, longitude 0° on purpose (in the Gulf of Guinea, far from any road), station
and vehicle names say "synthetic", and the first lines of every generated CSV say:

```
# SYNTHETIC data generated by: ev33_gen --profile medium --seed 33
# Invented network, stations, vehicles and trips for testing - not real places or products.
```

`scenario.cfg` records `data_source = synthetic` and `source_note` (the generator command). The
CLI prints "(synthetic data)" in every run header, and the website and desktop app label each
city as synthetic. Results from these files are model outputs for testing and teaching; they must
not be presented as forecasts for a real city.

## File formats

All files are UTF-8 CSV with a header row; columns are matched **by name** (order does not
matter); `#` lines are comments; fields may be quoted. Optional columns are in brackets.

| File | Columns | Rules |
|---|---|---|
| `scenario.cfg` | `key = value` lines: `name, data_source (synthetic \| real \| mixed), source_note, budget_inr, target_soc, regen_efficiency, climb_kwh_per_m, reference_consumption, speed_kmh, battery_step_kwh, max_detour_km, grid_kw, window_min, session_min, horizon_h, min_session_min` | unknown keys are errors; ranges checked (for example `0 < target_soc ≤ 1`, `0 ≤ regen_efficiency ≤ 1`) |
| `nodes.csv` | `id, [lat], [lon], [elev_m], [type], [name]` | unique integer ids; lat ∈ [−90, 90], lon ∈ [−180, 180], both or neither |
| `roads.csv` | `id, from, to, distance_km, [travel_time_min], [energy_kwh]` | unique ids; both ends exist; no self-loops; 0 < distance ≤ 100,000 km; roads are two-way; parallel roads allowed |
| `stations.csv` | `id, node, power_kw, ports, [name], [connector], [status], [install_cost_inr], [maint_period_h], [maint_offset_h]` | existing stations; status `available \| offline \| maintenance`; connectors like `CCS2\|Type2` |
| `candidates.csv` | `id, node, install_cost_inr, power_kw, ports, [name], [benefit], [suitability], [connector], [maint_period_h], [maint_offset_h]` | ids unique across stations and candidates; cost > 0; benefit ≥ 0 (estimated from trips when empty); suitability ∈ [0, 1] |
| `vehicles.csv` | `id, battery_kwh, charge_kwh, consumption_kwh_per_km, reserve_kwh, [model], [connector], [max_charge_kw]` | capacity > 0; 0 ≤ charge ≤ capacity; consumption > 0; 0 ≤ reserve < capacity |
| `trips.csv` | `id, vehicle, from, to, [depart_min], [start_charge_kwh]` | vehicle and nodes exist; start charge ≤ capacity (default: the vehicle's `charge_kwh`) |
| `sessions.csv` | `id, station, start_min, end_min` | booked sessions at an existing station or candidate; end > start |
| `events.txt` | one character per station event: `I` idle, `C` charging, `E` end of session, `F` fault, `O` out of service, `R` repaired | optional; used by Huffman coding and the string matchers |

Money is written in rupees with at most two decimals and stored exactly as integer paise.
Loading stops at the first problem with `file:line: reason` (see `docs/testing.md`, IT05 and
AD01–AD21), and nothing partially loaded is kept.

## Using real-world data

EV33 can run on real data if it is converted to the formats above. Suggested sources and steps
(none of this is automated in the project; it is guidance):

1. **Road network** — export a region from **OpenStreetMap** (for example with the Overpass API
   or a Geofabrik extract, © OpenStreetMap contributors, ODbL licence). Keep drivable ways
   (`highway=*` road classes), split them at intersections, write intersections as `nodes.csv`
   (OSM node id, lat, lon) and the segments between them as `roads.csv` with the haversine or
   way length as `distance_km`. Attribute OpenStreetMap wherever results are shown.
2. **Elevation** — sample a digital elevation model (for example SRTM, NASA, public domain) at
   each node for `elev_m`; leave it at 0 if unknown (flat model).
3. **Existing chargers** — public registries such as OpenChargeMap (check its licence and
   terms) or an operator's own list; map each charger to its nearest road node.
4. **Candidate sites and costs** — from the planning authority or operator; costs in rupees.
5. **Vehicles** — use published battery capacity and measured consumption for the vehicle
   classes in the study; record the source in `source_note`.
6. **Trips** — from a survey, a travel-demand model or anonymised, aggregated fleet data.
7. Set `data_source = real` (or `mixed`) and describe every source, date and licence in
   `source_note`, then run `ev33 validate --data DIR`.

### Privacy and ethics with real data

* Trip data can identify people (home and work locations). Use aggregated or anonymised origin
  and destination zones, never raw GPS traces of identifiable drivers, and follow the data
  owner's terms and applicable law (in India, the Digital Personal Data Protection Act, 2023).
* Placement by benefit score favours areas where demand is already measured; check whether
  low-income or rural areas are under-served before acting on a result, and treat the
  placement as one input to a decision made by people.
* State the energy model's simplifications (`docs/algorithms.md`, section 3) whenever results
  are shared; a feasible plan is a model result, not a guarantee that a real vehicle will make
  the trip, so keep a safety margin above the reserve in any driver-facing use.
